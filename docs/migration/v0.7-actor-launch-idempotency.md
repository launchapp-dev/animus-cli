# v0.7 actor-scoped workflow launch idempotency

`animus workflow run` now accepts `--idempotency-key <KEY>` for authenticated,
detached subject launches. This is additive; local/system runs without the flag
retain their existing behavior.

## Caller migration

Application transports should pass their validated HTTP `Idempotency-Key`
through unchanged:

```text
animus workflow run <workflow-ref> \
  --subject-id <kind:id> \
  --actor-json <transport-asserted-actor> \
  --idempotency-key <caller-key>
```

The actor must contain non-empty `user_id` and `tenant_id`. The project boundary
is the CLI's resolved `--project-root` repository scope; no caller-supplied
project id is trusted. Keys are limited to 128 bytes and the Portal-compatible
alphabet `[A-Za-z0-9._:-]`.

The same key and effective request replays the exact stored canonical run. A
changed workflow, subject, input, vars, override, actor, workspace, or project
does not reuse the reservation. Same-partition changes return
`idempotency_conflict`; other partitions cannot address or discover the row.
A concurrent or unexpired pending request returns `idempotency_in_progress`.

## Storage migration

On first keyed launch, the kernel opens the repo-scoped `workflow.db` in WAL
mode and transactionally applies `CREATE TABLE IF NOT EXISTS
workflow_launch_idempotency`. Existing databases need no offline migration.
The primary key is `(project_scope, workspace_id, actor_id, caller_key)` and the
row stores the request hash, effective workflow/subject binding, a preallocated
workflow id, lease ownership, and the completed canonical response.

The reservation is intentionally kernel-owned even when an installed
`workflow_journal` plugin owns run records. Existing journal `save`, `load`, and
actor-sidecar operations are sufficient; no workflow-runner or journal protocol
upgrade is required. If the external journal is unavailable during recovery,
the kernel fails closed instead of assuming the reserved run is absent.

## Crash recovery

The workflow id is reserved before journal creation or process spawn. A process
must still own the five-minute lease immediately before spawning. After a
restart, an unexpired row reports in-progress. Once expired, one process can
atomically reclaim it, load/create the same workflow id, repair a missing actor
sidecar from the scoped reservation, and either observe the live runner or spawn
one replacement. A superseded process cannot complete the reservation.

Portal deployments that also reserve the HTTP request may keep that outer
store. Passing the same key into this CLI surface closes the crash window
between Portal reservation and runtime launch. Portal should treat the two
named conflict outcomes as retry/reconciliation states and continue projecting
the canonical CLI run response.

Forwarding the key is necessary but is not sufficient if Portal leaves an
outer reservation permanently pending after its own process crashes. Portal's
outer store must either lease and reclaim stale pending rows or retry the same
CLI command during reconciliation. Replicated launchers must also share the
repo-scoped `workflow.db` on durable storage (or retain distributed admission in
the outer store); separate host-local databases cannot coordinate one launch.
